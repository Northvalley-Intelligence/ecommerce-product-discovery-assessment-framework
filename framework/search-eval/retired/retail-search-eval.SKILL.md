# Retail Search-Relevance Evaluation

Turn-key, cross-vertical workflow to evaluate any ecommerce store's on-site search: profile the real shopper engine, capture a query pack against it (no server load), grade result relevance with a pinned local LLM judge, overlay Google demand, split fixable search-bugs from assortment gaps, and ship a branded report + dashboard board. Started as furniture-specific; generalized to any retailer.

## When to use
- "Evaluate / benchmark <store>'s search", "why is <store>'s search bad", "find broken searches", "rank search fixes by demand".
- Compare stores, or a legacy storefront vs a new one it is migrating to.
- Build a search-relevance evaluation board or a client-ready findings report for an ecommerce store.

## READ FIRST — the lessons that make or break validity

1. **Measure the REAL shopper search engine, not a convenience API.** The single biggest trap. Pick the capture method by platform:
   - **WooCommerce** — storefront `https://<domain>/?s=<term>&post_type=product` (server-rendered HTML). Do **NOT** use the Store API `/wp-json/wc/store/v1/products?search=` — a *different, sparser* engine (accent chair: API 0 vs storefront 6). See `scripts/capture-storefront.mjs`.
   - **Shopify (custom/headless)** — the search box builds a strict **AND-of-prefix** Storefront GraphQL query per word: `(title:WORD* OR product_type:WORD* OR vendor:WORD* OR tag:WORD*)` all ANDed, `first:8`. A loose `products(query:)` is much fuzzier. Capture the page's actual in-session request. See `reference/shopify-predictive-capture.md`.
   - **Enterprise custom (Target, Home Depot, Lowe's, Walmart)** — React/Next.js behind bot protection; results fetched client-side. **Use the store's clean organic search API with sponsored excluded** (e.g. Target `redsky.../plp_search_v2?...&include_sponsored=false`), captured in-session at a **human pace**. Do NOT read all product links from the rendered DOM — see lesson 8. See `reference/enterprise-browser-read.md`.
   - When numbers look surprising, **verify against the live UI before trusting them.** (A Woo, a Shopify, AND a Target mistake were each made and corrected mid-project; the story flipped once fixed.)

8. **VERIFY THE WORST BEFORE REPORTING — the lowest-scoring terms are the most likely capture artifacts.** A term scores badly for one of two reasons: the search really failed, or the *capture* failed. The bottom of the ranking is disproportionately the latter. **Before any bottom-N (lowest NDCG / lowest grade) term becomes a finding, re-open it in the live shopper UI and confirm the captured results match what a shopper actually sees.** Real example: a Target board showed `dyson v8 → Clorox cleaning wipes, grade 0.60` — a false negative. The capture had grabbed a *"Recommended for you"* carousel, not the organic results; searching dyson v8 on the live site returns Dyson. Always sanity-check the worst before you ship them.

9. **Enterprise DOM reads are unreliable — carousels contaminate them.** Big-box PLPs interleave `Related to your search` / `Recommended for you` / sponsored carousels (containers with `data-test*=carousel`, cards `productCardVariantMini`) that render **above or instead of** the organic grid, and the organic grid sometimes does not render at all in an automated session. A naive `a[href*="/p/"]` selector then captures carousel/sponsored tiles, not real results — making the store look far worse than it is. Mitigations, in order: (a) use the clean organic API (`include_sponsored=false`) — the reliable source; (b) if reading the DOM, capture ONLY links whose ancestry contains no carousel container, and treat "no organic grid found" as 0 organic (never fall back to carousel tiles); (c) pace API calls to a human rate — a burst of rapid calls trips PerimeterX, which returns a 403 CAPTCHA that then blocks the whole session (recover by waiting for cooldown, not by bypassing it).

10. **Brand-name queries are keyword-API false negatives — they REDIRECT.** A pure house-brand query (Target: `threshold`, `cat and jack`, `good and gather`) returns **0 from `plp_search_v2`** even though the shopper sees thousands of products: the site 302-redirects `/s?searchTerm=<brand>` to a curated brand page (`/b/<brand>/-/N-...`, note the URL/title change to "<Brand> products at Target"). So a brand query looks like a total search failure in the API but is actually a *strength*. Rule: any surprising 0-result on a term that is a known brand → re-open live, and if it redirects to a brand page, record the brand page's results (count it answered), not the API 0. This is the same VERIFY-THE-WORST discipline as lesson 8, for a different mechanism.

11. **The bot-protection block is durable and per-visitor — wait it out, never rotate identities.** PerimeterX rate-blocks after ~15–28 *cumulative* calls per `visitor_id` in a session, and the block is **long-lived** (it did NOT clear after 20–40 min of quiet; it cleared only after an overnight gap). Each re-probe during a block resets its clock, so probe at most once per long quiet window. A *fresh* `visitor_id` immediately works — but deliberately rotating synthetic visitor_ids to punch through the limit is **bypassing bot protection and is prohibited**; recover only by waiting for a natural cooldown (single session identity). Practical cadence: capture ~15-term windows, then leave the store completely untouched until the block genuinely clears. Note also that from the store's HTTPS page in an automated session, the clipboard API, `fetch` to `http://127.0.0.1`, and server-side `curl` to the API (403) are all blocked — move captures to disk via an in-page global (`window.__CAP`, which survives fetch-only calls since you never navigate) read back in small sliced JS returns.

2. **Pin the judge rubric.** Cortex's default rubric can change. Record `rubric_hash` with every job (`cortex-poll.mjs` does). Deterministic only at a fixed rubric; re-run everything under one pinned hash.

3. **Validate the judge** on ~30 hand-labeled (query, product) pairs. Target high **binary** relevant-vs-not agreement (Industry West: 94%). The judge under-penalizes cross-category junk (grades 1 not 0) — conservative for a "noisy search" finding.

4. **Use the catalog as a guardrail.** A zero-result is a *search bug* only if the store stocks it; otherwise it is *true-empty* or an *assortment gap* (high demand, not stocked → merchandising, not search).

5. **No server load.** Bounded, paced reads (~1/sec), plain inspection UA (`Northvalley-Ecommerce-Inspection/0.1`), robots respected, no crawling/scraping loops. Never bypass bot protection or solve CAPTCHAs — read only what a real shopper's browser legitimately serves.

6. **Rank by demand.** Priority = search failure × Google search volume. Flag ambiguous head terms whose national volume is off-vertical (e.g. "buffet" = food, "console table" partly gaming) as indicative only.

7. **Relevance has grades, not just presence.** A big-box engine often returns *something* for almost anything, so coverage alone is misleading. Grade the top-8: a query can be "answered" but **shallow** (see the cross-vertical finding below).

## The flow
1. **Profile** → platform + real search engine + catalog (SKUs/categories/stocked types/materials where available).
2. **Dataset** → pick a query pack: `assets/general-retail-queries.json` (multi-department: home, kitchen, apparel, electronics, toys) or a vertical pack (e.g. a furniture pack). Both test the same dimensions: synonym/category equivalence, attribute (material+type), job-function/intent, head terms.
3. **Capture** with the matching method (Woo / Shopify / enterprise). Store per term: total (or display count), top-8 titles, and note sponsored tiles / category redirects.
4. **Grade** → `scripts/cortex-submit.mjs` + `scripts/cortex-poll.mjs` (Cortex `127.0.0.1:7077`, `llama3.2:3b`, temp 0, pinned rubric). NDCG + per-product 0–3 grades.

   **PIPELINE capture ‖ grade — both are slow, so overlap them.** Do NOT wait for all captures before grading. Capture a chunk, flush it to disk, and immediately submit it to Cortex (a background `cortex-submit.mjs` job returning a job_id) **while the next chunk captures**. Cortex grades chunk N while the browser reads chunk N+1, so wall-clock ≈ max(capture, grade), not their sum. Keep the list of job_ids; poll them all at the end (`cortex-poll.mjs <id1> <id2> ...`). Pin `rubric_hash` on every job. A single Cortex job holds many queries, so batch several terms per job.
     - **Enterprise API pacing dictates chunk size.** Big-box search APIs (Target Redsky, etc.) rate-limit on *cumulative* volume, not just burst — even ~1.7s-spaced calls trip PerimeterX (403 CAPTCHA) after ~20 in a session. So capture in **~15–20-term chunks per cooldown window** (wait ~60–90s between chunks; the block clears on its own — never bypass the CAPTCHA), and grade each chunk as it lands. The cooldown wait *is* the pipeline slack — fill it with Cortex grading of the prior chunk.
     - **Moving browser captures to disk fast:** the Claude-in-Chrome eval return is truncated (~850 chars), so don't slice large capture sets. Instead write them to the OS clipboard from the page (`await navigator.clipboard.writeText(JSON.stringify(caps))` — needs focus, so click the page/search box first) and read them with `pbpaste > file.json` in Bash. One write, one read, no slicing. (Keep captures in a page global like `window.__done` keyed by query so a re-fired capture loop resumes only the missing terms; do NOT navigate away — navigation wipes page state.)
     - Item shape varies (plain title strings vs `{t}`) — the submit script must handle both.
5. **Analyze** → coverage (zero-result rate), precision (mean grade, %not-relevant), **shallow-answer rate** (returns results but low grade), guardrail classification, and cross-store / old-vs-new comparison.
6. **Demand overlay** → `scripts/export-terms.mjs` → Google Keyword Planner → paste back → parse with `~/code/demand-data-generation` (`parse-keyword-planner-paste.js`) or the dashboard `/api/demand/import`. Split search-bugs vs assortment-gaps; rank by volume.
7. **Board** → assemble `eval-board.json`; render in the dashboard. **EVERY board — boutique two-store AND single-store/enterprise — MUST include all of: verdict card(s), per-dataset metric table, collapsed worst-first drill-down, the demand overlay affordance (Copy-terms + Paste-Keyword-Planner wired to `/api/demand/import?retailer=<id>&eval=<evalId>`), a Findings panel (from `eval-board.json` `findings[]`, severity-ranked), and the PDF link.** Do not ship a board missing the demand overlay or the findings panel — the single-store enterprise render (`loadRetailBoard`) originally omitted both and had to be back-filled to match the boutique render (`loadEvalBoard`). Routes: `/api/eval-board`, `/api/eval/rerun-ndcg`, `/api/demand/import`. For synonym datasets, annotate each row with `compared_to` (its canonical lead node) + `is_lead`, and show it in the drill-down (`term ↔ vs "canonical"` / `◆ canonical`) — per-term grades hide broken equivalence (e.g. `pop` grades 2.5 but returns Pop-Tarts, not soda).
8. **Report** → `scripts/gen-report.mjs` (or a per-store `gen-*-report.mjs` reading a `report-data.json` built by `build-report-data.mjs`) → **Northvalley-branded** PDF. **Required sections, in order: cover → Summary → How-measured → Findings (severity-ranked, one fix candidate each) → Demand-ranked quick-wins → How-we-can-help → per-dataset details → shallowest searches → Synonym equivalence (canonical vs variant, with Δ) → appendix (every term, # + NDCG + grade).** The Demand section uses real Keyword Planner volumes if `demand-volume.json` exists; otherwise it lists the failing-term fix candidates (grade < 1.5 on demand-mappable datasets, worst-first) and states volumes rank them once imported — **never fabricate search volumes.** Needs `northvalley-template-assets/` (brand.sty + logo); compile with `pdflatex` twice.

## Cross-vertical finding (from the Target pilot, 2026-08-08)
Enterprise engines and boutique engines fail **differently**:
- **Boutique (Industry West WooCommerce, Seven Bonde Shopify):** narrow — return **0** for synonyms (cocktail table), attributes (walnut dining table), and intent. The problem is *recall*.
- **Enterprise (Target):** wide — handles synonyms (cocktail table → 398 coffee tables) and attributes (walnut dining table → dining tables) that boutiques miss, **but** natural-language intent is **shallow, not dead**: it returns a plausible department instead of the specific ask. `furnish a living room` → 200 vases/candle holders/decor (not furniture); `gift for a 5 year old boy` → 674 teethers/baby rattles/batteries (ignores "5 year old"). The problem is *intent understanding / precision*, not coverage.
- **Implication:** for big-box, coverage looks great, so the eval must weight **grade quality and the shallow-answer rate**, not zero-result rate. Do not port the furniture "% zero-result" headline to a general retailer without this adjustment.

## eval-board.json / report-data.json
Same shapes as documented in `scripts/gen-report.mjs` header. For a single-store eval (no migration), the board still uses the two-column layout but the second column may be a competitor or omitted; verdict cards summarize coverage + %not-relevant + a shallow-answer note. **`eval-board.json` MUST carry a `findings[]` array** (`{severity: Critical|High|Medium|Low|Info, area, title, detail}`) — the board's Findings panel and the report's Findings section both read it; a board without `findings[]` renders no findings panel. Synonym rows additionally carry `compared_to` (canonical lead term) and `is_lead`. `report-data.json` is derived from the board by `build-report-data.mjs` and adds `equiv` (synonym groups), `findings`, `demand_candidates` (failing terms on demand-mappable datasets, worst-first), and `demand_volume` (null until an operator imports Keyword Planner data).

## Adapting to a new store (checklist)
1. Detect platform → choose the capture method (Woo / Shopify / enterprise) → confirm it's the **shopper-facing** engine.
2. Profile the catalog where accessible (enterprise sites usually expose no catalog API — rely on search + on-page signals).
3. Capture the pack; record totals + top-8 + sponsored/redirect notes.
4. Grade under a pinned rubric; validate the judge on a gold set.
5. Build `eval-board.json`; classify recall-miss vs true-empty vs assortment-gap vs **shallow-answer**.
6. Export terms → Keyword Planner → import volume → rank failures by demand.
7. Derive `report-data.json`; run `gen-report.mjs`; compile the branded PDF; wire the board + PDF link.
8. If the project uses MDE, record findings + a validation note. Add the store to its sector (`sectors/<sector>.json`).

## Do / Don't
- **Do** measure the shopper-facing engine, pin the rubric, validate the judge, use the catalog guardrail, grade quality (not just presence), rank by demand, keep reads bounded.
- **Don't** use a Store API / loose GraphQL as a proxy for shopper search, treat big-box coverage as quality, present head-term volume as addressable revenue, bypass bot protection or solve CAPTCHAs, fabricate screenshots (this sandbox can't save them — use live URLs / captured result text), or claim reproducibility without a pinned `rubric_hash`.
